# Progress and Motivation: Data Preparation Goal: prepare the project for motivation features (real streak, level and XP bar, daily goal ring, lesson completion states, weak words review, small celebration animations) by defining **what data exists, where it lives, and how it is accessed**, so the storage can move from `localStorage` to a database later without touching feature code. This document is theory and structure only. It describes variables, rules, and an access layer. It does not prescribe UI markup. > **Assumption:** `docs/MULTI_COURSE_PLAN.md` is fully done. That means course-aware pages, `js/course.js`, `js/storage.js`, `js/layout.js`, `js/blocks.js`, `courses/<id>/...` JSON packs, stable IDs for vocab, lessons, and exercises, and per-course namespaced storage. > **How to use:** tell the AI "do step N in docs/PROGRESS_AND_MOTIVATION.md". Steps are small and each leaves the site working. ## Progress - [ ] Step 1: Progress store with a swappable adapter - [ ] Step 2: Data model (user, course, daily, word, lesson) - [ ] Step 3: Derived values (streak, level, goal, lesson state) - [ ] Step 4: Recording points (where events are reported from) - [ ] Step 5: Weak words tracking - [ ] Step 6: Progress events and celebration hooks - [ ] Step 7: Config files (tunable rules) - [ ] Step 8: Database readiness (mapping, sync fields, migration) --- ## Principles 1. **Store facts, derive numbers.** Save raw things that happened (XP earned on a day, a lesson result, a word answered wrong). Compute streak, level, goal progress, and lesson display state from them. Never store a value that can be recalculated, except small cached aggregates. 2. **One module owns progress.** All reads and writes go through `js/progress.js`. No page or feature touches `localStorage` for progress directly. 3. **Async API, even for localStorage.** Every store method returns a Promise. Today it resolves instantly; later it can call a server with no caller changes. 4. **Everything is keyed by stable IDs** (`courseId`, `lessonId`, `vocabId`, date strings), never by array position or display text. 5. **Everything has an owner.** Even with no accounts, data belongs to a `userId` (`"local"` for now). A future login just replaces that value. 6. **Dates are the learner's local calendar days** (`YYYY-MM-DD`). Timestamps are ISO 8601 UTC. Store the timezone with the profile so streaks stay correct if the device zone changes. 7. **Rules are config, not code.** Level thresholds, pass score, daily goal defaults, and review rules live in `config/progression.json` so they can be tuned without code changes. 8. **Global vs per course** (consistent with the multi-course plan): XP total, streak, and daily goal are global. Lesson states and word stats are per course. --- ## Step 1: Progress store with a swappable adapter **Goal:** a single access layer that hides where data is stored. **Do:** 1. None of these are stored (except noted caches). **Streak** (global) - A day is *active* if `daily[date].xp > 0`. - `currentStreak` = number of consecutive active days ending today. If today has no activity yet but yesterday was active, the streak is still alive (shown as "at risk"), not zero. - `longestStreak` = longest consecutive run in history. - Optional later: a "freeze" (one skipped day allowed). Reserve the field `streakFreezes` on `profile`, don't implement yet. **Level and XP bar** (global) - `level` and `xpIntoLevel` / `xpForNextLevel` come from the thresholds in `config/progression.json` applied to `profile.totalXp`. - Bar fill = `xpIntoLevel / xpForNextLevel`. - Per-course XP (sum of `xpByCourse[courseId]` over all days) can be shown on course pages but doesn't affect level. **Daily goal ring** (global) - `todayXp = daily[today].xp`, `goal = daily[today].goalXp` (falls back to `profile.dailyGoalXp`). - Ring fill = `min(todayXp / goal, 1)`. `goalMet` is set to `true` the first time it reaches 1 that day. - Changing `dailyGoalXp` affects only today and future days. **Lesson display state** (per course) Combine content availability with learner state into one value used by the units page, roadmap, and lesson sidebar: | Content status | Learner state | Display state | |---|---|---| | `soon` / locked | any | `locked` | | `available` | none or `not_started` | `available` | | `available` | `in_progress` | `in_progress` | | `available` | `completed` | `completed` (show checkmark and best score) | A lesson becomes `completed` when `bestScore >= passScore` (from config) after its tasks are graded. Optional rule for later: the next lesson unlocks only after the previous one is completed. **Course progress summary** `completedLessons / totalAvailableLessons` for the current course (replaces typed text like "1/5 lessons available" and the hard-coded "1/16" in the profile modal). **Done when:** - [ ] Each value above has one function in `progress.js` (e.g. `getStreak()`, `getLevelInfo()`, `getDailyGoal()`, `getLessonDisplayState(courseId, lessonId)`). - [ ] The functions take stored facts as input and have no hidden state, so they can be unit-tested by hand. --- ## Step 4: Recording points **Goal:** list every place in the engine that must report an event, and the single function each calls. This replaces direct `addXP()` calls. | Where | Event | Call | |---|---|---| | Any correct answer or finished activity | XP earned | `recordXp({ courseId, amount, source, refId })` | | Lesson page opened | lesson started | `recordLessonOpened(courseId, lessonId)` (also updates `position`) | | Lesson tasks graded | lesson result | `recordLessonResult(courseId, lessonId, { score, xp })` | | Dictionary "learned" star toggled | word learned/unlearned | `setWordLearned(courseId, vocabId, bool)` | | Flashcards, dictionary quiz, exercises, answer | word answered | `recordWordResult(courseId, vocabId, isCorrect)` | | Exercise or answered | general answer | counts into `daily.exercisesAnswered/Correct` via `recordXp` or `recordAnswer` | | Page load of lesson, exercises, flashcards, | last position | `setPosition(courseId, { type, refId, url })` | Rules: - `source` is a short string (`lesson`, `exercise`, ``, `flashcards`, `dictionary`) kept so a future stats page or database report can group XP by origin. - `recordXp` is the **only** function that changes `totalXp` and `daily`. It also updates the daily goal and detects level-ups, streak increases, and goal reached (Step 6). - Once-per-activity rewards (the 's +50 XP, a lesson's best-score XP) are guarded by checking stored state, not by in-memory flags. **Exercises referencing words:** to feed weak words, exercise and items that test a word get an optional `vocabRefs: ["it-001"]` field in `exercises.json` / `.json`. Add it to `docs/schemas.md`. Items without it simply don't affect word stats. **Done when:** - [ ] No feature file calls `addXP()` or writes progress directly; all use the functions above. - [ ] The table above is reflected in a short "Recording points" comment block at the top of `progress.js`. --- ## Step 5: Weak words tracking **Goal:** know which words a learner struggles with, and be able to build a review set. **Recording:** every `recordWordResult` updates `wordStats` (`correct`/`wrong` counters, `correctInRow`, `lastResult`, timestamps). **A word is "weak" when** (rules from config): - `lastResult === "wrong"`, **or** - `wrong >= weakMinWrong` and `correctInRow < weakClearStreak`. **A word leaves the weak list when** `correctInRow >= weakClearStreak` (suggested default: 2). **Review set:** `getWeakWords(courseId, { limit })` returns weak words sorted by most recent wrong first, then by highest `wrong` count. A review session (future UI: a "Practice mistakes" chip or button on flashcards) is just flashcards or a quiz fed by this list. **Review results** are recorded like any other word result, so words clear themselves naturally. **Empty state:** when the list is empty the UI shows "No weak words yet", not an error. **Done when:** - [ ] `getWeakWords()` works from stored data alone. - [ ] The weak/clear rules read their numbers from config (Step 7). --- ## Step 6: Progress events and celebration hooks **Goal:** let the UI react (progress bar update, small animations) without feature code knowing about animations. **Event bus:** `progress.js` dispatches `CustomEvent`s on `window`. The UI listens, and progress code never touches the DOM. | Event name | `detail` | Fired when | |---|---|---| | `progress:xp` | `{ amount, totalXp, source }` | any XP recorded | | `progress:levelUp` | `{ level }` | level increased and `level > lastCelebratedLevel` | | `progress:goalReached` | `{ date, goalXp }` | today's goal met for the first time | | `progress:streakIncreased` | `{ currentStreak }` | first activity of a new day extends the streak | | `progress:lessonCompleted` | `{ courseId, lessonId, score }` | state first becomes `completed` | | `progress:wordLearned` | `{ courseId, vocabId }` | word marked learned | | `progress:changed` | `{ collection, id }` | any write (generic refresh signal) | **Effects layer (future UI):** a separate `js/effects.js` subscribes to these events and decides what to show (confetti on `lessonCompleted` and `levelUp`, a pulse on the ring for `goalReached`, a small "+10 XP" float for `progress:xp`). Rules for effects: - Respect `prefers-reduced-motion` and `profile.effectsEnabled`; do nothing when either says off. - Celebrations fire once per real achievement; use stored flags (`lastCelebratedLevel`, `goalMet`, lesson `completedAt`) so reloading or revisiting never replays them. - Effects must never block interaction and must clean up their DOM. - Header widgets (streak badge, XP badge, goal ring, level bar) re-render on `progress:changed`. **Done when:** - [ ] All events above are dispatched from `progress.js` only. - [ ] A listener can be added or removed without changing any feature file. --- ## Step 7: Config files **Goal:** keep tunable rules out of code. Create `config/progression.json`: ```json { "dailyGoalDefault": 50, "dailyGoalOptions": [20, 50, 100], "passScore": 0.7, "levels": { "type": "linear", "xpPerLevel": 100 }, "xp": { "mcq": 15, "blank": 10, "reorder": 10, "match": 20, "lessonComplete": 50, "wordLearned": 5, "customWordAdded": 25 }, "weakWords": { "weakMinWrong": 2, "weakClearStreak": 2 }, "dayStartsAtHour": 0 } ``` Notes: - `levels.type` allows a future `"curve"` option (custom thresholds array) without code changes. - The `xp` table replaces numbers currently scattered in `exercises.js`, `dictionary.js`, `.js`, and the lesson JS. An item's own `xp` field (from the exercise schema) overrides it. - Optional per-course override: `courses/<id>/course.json` may include a `progression` object that overrides keys above. - `dayStartsAtHour` lets the "day" roll over at, say, 4 AM for late-night learners. It defaults to 0. **Done when:** - [ ] No XP or rule numbers remain hard-coded in feature files. - [ ] Changing a value in the config changes behavior with no code edits. --- ## Step 8: Database readiness **Goal:** make the later move to a real database mechanical. **1. Collection to table mapping** | Collection | Future table | Primary key | |---|---|---| | `profile` | `users` / `profiles` | `userId` | | `daily` | `daily_activity` | (`userId`, `date`) | | `lessonProgress` | `lesson_progress` | (`userId`, `courseId`, `lessonId`) | | `wordStats` | `word_stats` | (`userId`, `courseId`, `vocabId`) | | `position` | `last_position` | (`userId`, `courseId`) | | `customWords` | `custom_words` | (`userId`, `courseId`, `wordId`) | Course content (vocab, lessons, exercises) is **not** in the database. It stays in the JSON packs, and progress rows only reference its IDs. **2. Sync fields.** Every record has `updatedAt`. Conflict rule when syncing later: for scalar fields the newer `updatedAt` wins; for counters (`xp`, `correct`, `wrong`) take the maximum, and for `bestScore` take the maximum. Keep these rules in a short comment so a server implementer follows the same logic. **3. Offline-first.** The `ApiAdapter` should write to the local adapter first and queue changes for upload. Keep this possible by never assuming a write is instantly remote. **4. Schema versioning.** `profile.schemaVersion` plus a `migrate(fromVersion)` function in `progress.js`. The first migration imports the legacy keys (`ls_xp`, streak placeholder, dictionary learned list, best lesson XP) into the new collections once, then marks it done. **5. Account upgrade path.** When login arrives: keep the local data, assign it to the new `userId` on first sign-in, and upload through the adapter. No feature code changes. **6. Export/import (cheap safety net).** Add `exportProgress()` and `importProgress(json)` returning/consuming all collections as one JSON object. It's useful for backups now and for server migration tests later. **Done when:** - [ ] The table mapping and conflict rules are documented in `docs/schemas.md`. - [ ] `migrate()` exists and runs once on first load with old data. - [ ] `exportProgress()` output can be re-imported to an empty browser with identical results. --- ## Out of scope for now - The UI itself (ring, level bar, checkmarks, review button, confetti visuals). This document only prepares data and hooks. - Achievements/badges, leaderboards, streak freezes, and spaced-repetition scheduling. The data model leaves room for them (extra fields, `wordStats` timestamps). - Real accounts and a server. Step 8 only prepares for them.
